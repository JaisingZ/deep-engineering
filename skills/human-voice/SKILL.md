# 活人感写作

把一篇中文技术文写成「人在场」：先是亲历，然后才是道理。人味靠现场细节、具体数字、第一人称的判断和一句短收尾，不靠口语堆砌，也不靠热梗。

依据是作者本人 78 篇掘金文章的统计和原句，见 [references/style-analysis.md](references/style-analysis.md)。可检查的阈值在 [config/style-rules.md](config/style-rules.md)。

## 已定口径

这五条已经定死，写的时候直接照做。

- **口语克制。** 只用「就是」「比如」「一下」，偶尔一个「好家伙」。网络热梗一篇最多一个。
- **不用 emoji。** 标题、列表、结尾都不用。
- **轻自嘲 1 到 2 处。** 点一下即可，例如「又是被祖传代码教做人的一天。」不把自嘲写成整篇的笔调。原作者几乎不自嘲，这是故意加上的一点。
- **标题以亲历型为主。** 「记一次…」，或者「具体对象 + 具体动作或结果」。问句和反差钩子可以用，适合发到 X。
- **段长不超过 120 字（大约 3 行）。** 不规定整篇字数。

## 怎么用

分两遍。一遍写完再检查，不要边写边装成清单。

### 起草

1. 标题先按亲历型起一稿。开头三句写清：谁、什么时候、碰到了什么事。
2. 按发生顺序写。第一次没成、问错人、参数抄错，留在正文里。数字写上场景，不写「大量」「显著」。
3. 一段一个意思。写超三行就拆开，拆完接一句短的，用来转场或下判断。
4. 代码或截图前写一句白话，后面写一句结论。
5. 收尾只留一句短话。判断、感受或下一步，三选一。

不编造没有发生过的经历、数字和人物。原文里有的失败和零碎细节不要抹平。原文没有自嘲时，可以补 1 到 2 句不引入新事实的轻自嘲。

### 复核

1. 删模板连接词和空词（见下方避免清单）。一段里不要叠「不仅…而且…更」或「既…又…还」。
2. 数四样：加粗不超过 5 处，emoji 为 0，热梗最多 1 处，轻自嘲 1 到 2 处。
3. 每个数字问一句：场景、基线或时间在不在。没有就补上下文，或者删掉这个光秃秃的数字。不要为了「具体」新造一个数。
4. 看结尾是不是一句短话。看有没有至少一处一句话成段。
5. 对稿子跑检查脚本，再用人看脚本判不了的几条：

```bash
python3 skills/human-voice/scripts/lint.py path/to/article.md
```

脚本读 [config/style-rules.md](config/style-rules.md)。它能抓住禁用词、emoji、加粗数量、段长、连接词链和层层叠加。自嘲、标题口吻、数字有没有场景，要人看。

## 十二条

### 1. 先写「我遇到了什么」，再写道理

开头三句要交代：谁、什么时候、碰到了什么事。

- 改前：多数据源切换是一种常用的基础组件，具有重要意义。
- 改后：上周接手一个老项目，MySQL 和 Clickhouse 来回切，偶尔会查错库。

### 2. 数字要具体，要带场景，别凑整

用 13575 次、1.6W、三万多，不用「大量」「显著」。数字旁边要有基线、环境或时间。

- 改前：线程数大幅增加，最终导致内存溢出。
- 改后：一天 1.6W 次访问，就新建了 1.6W 个线程池，不到两天就 OOM 了。

### 3. 写出过程里的插曲和失败

第一次没成功、问错了人、参数抄错了，都留着。

- 改前：通过调整参数成功解决了问题。
- 改后：大模型给的前缀还是 server.tomcat，不对，我又追问了两轮才改过来。

### 4. 每段不超过 120 字，长段后面接一句短的

大约 3 行。短段用来转场或下判断。段落长短要有起伏，不要每段都一样齐。不规定整篇字数。

- 改前：（一段 250 字的分析，最后顺带提一句结论）
- 改后：……（80 字分析）／翻开这个接口，感觉离真相很近了。

### 5. 判断用第一人称，并且留一点余地

多用「我理解」「我的判断是」「我持谨慎态度」。把结论说死之前，先写自己还在看什么。

- 改前：AI 编程必将彻底取代传统开发模式。
- 改后：我觉得这事迟早会发生，但眼下我还是会先看一遍它生成的每一行代码。

### 6. 口语只用一点点

像同事聊天，不像主播。可以用「就是」「比如」「一下」，偶尔「好家伙」。网络热梗一篇最多一个。不用「啊 / 呀 / 咱 / 说白了」，也不用「绝绝子 / 破防 / 家人们谁懂」。

同一篇里另放 1 到 2 处轻自嘲，点到为止。像「又是被祖传代码教做人的一天。」不要写成一整段卖惨。

- 改前：家人们谁懂啊，这个 bug 直接给我整破防了！！！
- 改后：好家伙，几分钟内就报了 13575 次。

### 7. 括号里写只有动过手的人才知道的细节

坑点、前提、权限放进括号。

- 改前：使用 jmap 导出堆转储文件即可。
- 改后：用 jmap 导出堆转储（记得切到服务启动账户，root 也 dump 不出来）。

### 8. 代码和截图前一句白话，后面一句结论

例如「写法是这样的：」「一次通过。」不要写「如下图所示」。

- 改前：如下图所示，程序运行结果符合预期。
- 改后：不改任何东西直接跑，一次通过。

### 9. 标题用亲历型

「记一次…」，或者「具体对象 + 具体动作或结果」。报错名、工具名、数字可以进标题。问句和反差钩子可以用，例如「使用数据库作为接口还怕难以测试？@DataJpaTest 稳稳接住」。

- 改前：浅谈线程池的最佳实践与思考
- 改后：记一次线程池误用导致线上 OOM 的排查过程

### 10. 结尾落一句短话

一句 6 到 15 字的判断、感受或下一步。不写总结清单，不预告「下面从三个方面」。

- 改前：综上所述，本文介绍了 A、B、C 三个方面，希望对大家有所帮助。
- 改后：没有比 Deadline 更好的生产力了。

### 11. 允许一句和主题无关的生活细节

一篇最多一两处，用来证明「我当时在场」。没有发生过的不要编。

- 改前：入职第一天，我迅速融入了团队。
- 改后：中午想约大家吃饭，结果一半回家一半带饭，没约成。

### 12. 一个道理只说一遍，用一个例子

不要再用排比或换个说法重复一遍。

- 改前：提升效率、优化体验、赋能业务，打造高质量研发体系。
- 改后：测试同学少等半天环境，这个改动就值了。

## 要避开的 AI 味

- **模板连接词**：首先 / 其次 / 再次 / 最后连成一套、综上所述、总而言之、值得注意的是、不难发现、由此可见
- **空洞大词**：赋能、助力、抓手、闭环、底层逻辑、打造、全方位、多维度、深度融合、生态、范式
- **层层叠加**：一段里出现「不仅…而且…更…」，或者「既…又…还…」。单独一次「不仅…而且」可以，叠成三层不行
- **排比和四字格**：三连或四连的对仗短语（「上强度、提效率、促协同」这种也算）
- **空总结**：文末「总结一下：1. 2. 3.」复述正文，「希望对你有所帮助」「欢迎点赞关注」
- **加粗关键词加冒号的列表**：`* **消除竞态条件**：……`。全篇加粗超过 5 处也算多
- **emoji**：不用。✅❌⚠️🚀💡 开头的列表尤其不要
- **标题太碎**：1500 字的文章拆出 20 多个小标题；每节都是「概述 / 原理 / 实践 / 总结」
- **四平八稳的结论**：「各有优劣，需根据实际场景选择」「合理的设计可以成为有效工具」
- **假设性开场**：「在当今快速发展的时代……」「随着某技术的不断发展……」
- **段落长度太整齐**：每段都是 2 到 3 句、长度差不多，没有一句话成段的地方
- **光秃秃的成绩**：「性能提升 50%」，但没有基线、环境，也没有翻车过程

单独出现的「最后」不必删。「最后一步」是正常说法。它和「首先 / 其次 / 再次」凑成一套时才要拆掉。

## 写完对照

- [ ] 加粗不超过 5 处
- [ ] emoji 为 0
- [ ] 没有「首先 / 其次 / 再次 / 综上所述 / 总而言之 / 值得注意的是」
- [ ] 没有把「不仅…而且…更」或「既…又…还」叠在同一段
- [ ] 每个数字都有场景（基线、环境或时间）
- [ ] 结尾是一句短话，没有总结清单
- [ ] 段落不超过 120 字，并且至少有一处一句话成段
- [ ] 口语停在「就是 / 比如 / 一下」，热梗最多一处
- [ ] 轻自嘲 1 到 2 处
- [ ] 标题是亲历型，或是一个问句 / 反差钩子

## 文件

- [config/style-rules.md](config/style-rules.md)：阈值、禁用词、允许的口语。检查脚本只读这份。
- [references/style-analysis.md](references/style-analysis.md)：78 篇的统计和原句，写规则时用来核对，不要把里面的原句改写进新文章冒充自己的经历。
- [scripts/lint.py](scripts/lint.py)：只依赖 Python 标准库。退出码 0 是通过，1 是有违规，2 是文件或配置打不开。
