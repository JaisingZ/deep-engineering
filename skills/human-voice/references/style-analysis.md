## 2. 标题模式

平均标题长 26 字。统计：含“——”33%，含“与”38%，系列编号（一/二/三）14%，以“分析/浅析/解析/初探/一览/简介”结尾 21%，含数字 17%，问号/感叹号只有 3%。

几种固定套路（全部是原标题）：

1. **主副标题，主标题是比喻或成语**：`先胜而后战——领域驱动设计中的最小闭环入门实践方法`、`使众人行——项目管理的思维框架初探`、`良好开端是成功一半——不能忽视的项目启动会`、`业务与技术沟通的桥梁——领域驱动设计中的领域建模`
2. **“A 与 B”并列，问题加原理**：`Too Many Open Files 与 Linux 系统资源控制`、`PF4J 日志类冲突与 JVM 类加载机制`、`Consul 健康检查异常、丢包与 Linux 网络问题排查`
3. **系列加口语化的系列名**：`JetBrains AI 打零工（三）——Junie 常用交互模式分析`、`架构思维（一）成为架构师的第一步——程序员的架构思维转型`
4. **“记一次 / 初体验 / N 小时”的亲历型**：`记一次线程池误用导致线上 OOM 故障的排查与解决过程`、`Trae 初体验，不写一行代码完成 Request header is too large 问题修复`、`Trae Builder 一小时，生成一个仿掘金主页的 Web 工程`
5. **人生节点型**：`第三季，入职半个月的开发体验`、`入职三个月，新工作走向正轨`、`提前转正述职，迈过入职甜点位`
6. **很少见的口语钩子**（全库只有一篇）：`使用数据库作为接口还怕难以测试？@DataJpaTest 稳稳接住`

高阅读量标题有个共同点：**具体的报错或技术名词＋动作**（OOM、Too Many Open Files、MySQL 迁移达梦、Request header is too large）。

## 3. 开头模式：前三句怎么钩人

列出 78 篇的前三段后，大致分五类：

| 类型 | 占比(约) | 例子 |
|---|---|---|
| A. **直接上二级标题**（`## 一、问题现场` / `## 1.事件风暴是什么`），没有引子 | ~45% | 技术教程、DDD 系列几乎都这样 |
| B. **一句短句点明“这次干什么”** | ~20% | 「Trae 出了 Windows 版本，今天试一试看看手感如何。」 |
| C. **承接上一篇** | ~10% | 「上一篇我们看到了 Mybatis 拦截器在多租户场景下的使用，这次继续看下在主键生成场景下的应用。」 |
| D. **时间加处境叙事** | ~10% | 「时间来到 2024 年 10 月中旬，由于公司组织架构调整……我决定离开工作四年半的公司出来看看。」 |
| E. **一句格言/金句/节日问候** | ~10% | 「工作步入第八年，越来越发现工程能力的重要性。」「龙行龘龘，开工大吉！」「用发展的眼光看未来，用成就的视角看现在。」 |

**效果最好的开头**（亲历型）一般是三拍：
1. **一句短的处境句**（我接到了什么 / 什么出了新版本）
2. **一句给出反差或悬念**（“原因其实不复杂，但……酿成大祸”、“每次都没有经过任何处置就会自行恢复”）
3. **一句交代本文路线**（“下面就来回溯下问题排查过程，逐步进行，逐层深入……”）

> 「最近接到了一个线上问题处理任务……最终定位到问题发生的原因其实不复杂，但是往往因为粗暴的开发模式容易导致简单的问题酿成大祸。」——《记一次线程池误用导致线上 OOM…》

弱点：大量技术文直接从定义开始（“多租户指的是……”），没有钩子，读起来像文档。

## 4. 结构与节奏

- **标题密度**：平均每篇 10.1 个标题（早期 8.3，2025-09 后 AI 化文章 35.8），74/78 篇有标题
- **编号习惯**：`## 一、` → `### 1、` → `（1）`，中式公文层级；早期用 `1.`；DDD 系列用 `1.1`
- **亲历型文章的骨架**（排查文最典型）：
  `问题现场（业务背景→问题表象→紧急处理）→ 问题排查（逐层）→ 修复/测试 → 回顾总结`
  每一层都是“看到现象 → 猜测 → 用命令/日志验证 → 下一步”，跟真实排查顺序一致
- **叙事型文章**（入职、面试）：按时间推进，小标题像日记章节——`紧迫的入职窗口`、`波澜不惊的第一天`、`难说清的版本分支`、`第一个需求实现`
- **节奏手法**：长段讲完一层之后，常常**单独放一句短段做转场或定性**：
  「接下来，就是惊心动魄的问题排查阶段。」「于是，可以大胆猜测该功能存在无用线程池的问题，下面可以分析代码了。」「插曲毕竟都是插曲，只会让我的目标更清晰。」
- **代码**：39/78 篇有代码，平均每篇 5 个代码块；代码前一般用一句口语引出，比如“写法是这样的：”“调用时就变成了这样：”“请求体是这样的：”
- **截图**：41/78 篇有图，平均每篇 2.1 张；工具实测文几乎每一步配一张截图，配一句很短的评语（“不做调整，直接运行，一次通过。”）

## 7. 具体素材怎么用

- **数字是活人感的第一来源**，而且数字一定挂着场景：
  「这似乎存在某种关联，放开的业务功能每天的使用量是 1.6W，默认线程池名称的线程数是三万多，发生 OOM 的时间是不到两天。」
  其他例子：“一台 64G 内存的高配 CentOS 物理机”“集群超过八十台服务器”“11 家面试 3 个 Offer”“三个晚上整理简历”“十一点多提交了最后一段补丁”“线程数稳定在四百多”
- **过程里的小插曲和失败**：Offer 试用期和转正薪资被写反；版本分支有十几个、找了几个人才对上；大模型给的参数前缀不对、要“继续质疑一下”；删了 target 跑不起来；面试“多次挂在技术二面”
- **括号补充的实操经验**：「（记得切换到服务启动的账户，如果不是，使用 root 都不能成功 dump）」「（线上添加启动参数需要检查远程监控端口是否被占用）」，这种只有动过手的人才写得出来
- **代码**：贴的是真实业务里的错误写法加修正，不是玩具示例；注释也带情绪：`// 祖传代码业务耦合过高，解析上传结果都不舍得分离的`
- **截图**：一步一图，每张图配一句结论

## 9. 为什么像真人，不像 AI

1. **有“我”在场，且做了具体动作**：先找运维聊背景，再看代码；蹲守问题现场；拿起笔画图
2. **细节有零碎感**：午饭没约上、顺手擦了烧水壶桌面、灯一关大家支起躺椅午睡，这些和主题无关，但很真
3. **数字不圆**：13575 次、1.6W、三万多、四百多、十一家
4. **判断有态度、有保留**：“我也是持谨慎态度的”“我的判断是不能简单归因，先解决问题”
5. **节奏不均匀**：长段后面突然接一句 6 个字的短句；有的章节很长，有的只有两行
6. **有小瑕疵**：错别字（“花了起来”应为“画了起来”、“丢到到”、“hava”）、偶尔重复用词。这不必模仿，但说明它不是机器打磨的
7. **收尾不总结，只落一句**

对照：作者 2025-09 后的文章出现了典型 AI 痕迹，例如「通过合理的设计和实现，自定义拦截器可以成为解决特定场景问题的有效工具。」，以及满屏的 `* **消除竞态条件**：…` `⚠️ 实现和维护成本较高` 这种“加粗关键词＋冒号＋短语”列表。

## 10. 作者从不（或几乎不）做的事

- 从不用“啊、呀、咱、说白了、居然、竟然”，emoji 只在 AI 化文章里出现
- 从不用“综上所述 / 总而言之 / 值得注意的是 / 底层逻辑 / 抓手”
- 几乎不用感叹号和问号标题（3%）
- 不写“大家好，我是 xxx”，不求点赞关注，不加“如果对你有帮助”
- 不夸大，不用“震惊 / 必看 / 吊打”
- 不讲段子，不刻意制造梗
- 不在文末堆“总结一下：1. 2. 3.”的空总结（AI 化文章除外）

**作者自己也有、但写 Skill 时不建议照搬的“半 AI 味”习惯**：四字词排比（“上强度、提效率、促协同”“跑得慢、改不动、读不懂”）、“不仅……还……更是……”层递、抽象名词堆叠（“加速知识循环、消解知识壁垒”）、方法论式升华结尾。
